ここからの実践提案は、モデルだけを変更し、Repository、仕様、Agent指示、テストを固定することです。ContextはAIに渡す情報、HarnessはToolsや実行手順・評価を含む周辺の仕組み、と考えると整理しやすくなります。

- 機能テストが通ったかだけでなく、認可・監査のルールを守ったかを記録する。
- 不明点を質問したか、不足情報を捏造したかを確認する。
- 完了までの時間と人による修正時間を測る。
- 高いモデルへ切り替える前に、失敗原因が仕様不足かを確認する。

## 6. 仕様駆動開発：モデルが変わっても品質基準を残す

今週の学習テーマは、Requirements → Design → Tasks → Implementation → Test / Evidenceのつながりです。最初から大きな仕様書を作る必要はありません。小さなAPIの振る舞いを明文化し、実装がその条件を満たすか確認できれば、最初の一歩として十分です。

| 成果物 | Java業務APIでの例 | 確認すること |
| --- | --- | --- |
| Requirements | 本人だけが明細を参照できる | 誰に何を許可するかが明確か |
| Design | 認可チェック、例外、監査の配置 | 業務共通Frameworkの規約に沿うか |
| Tasks | 実装・テスト・文書更新の小タスク | テストが最後に抜け落ちていないか |
| Implementation | APIと認可処理 | 仕様外の変更が混ざっていないか |
| Test / Evidence | 成功・未認証・他人の明細の試験 | 要求と結果を対応付けられるか |

Kiroの10月30日記事は背景資料として再確認。Specification Hardeningは要求文の兆候からCWEに基づくセキュリティ要件を提案しますが、コードの安全性を証明したり、SAST・DAST・人間のレビューを代替したりするものではありません。

出典：[Kiro — Spec it safe（10/30・背景）](https://kiro.dev/blog/spec-it-safe/)

重要なのは、自然言語で作れた設定が正しいとは限らないことです。まずは読み取り → 提案 → 構文と影響の検証 → 承認 → 適用 → 監査という手順を分けます。TerraformやKubernetes Manifestでも、同じように変更前の確認と変更後の証拠を残す練習ができます。これは編集部の運用提案です。

Googleの発表は、適合・非適合のテスト用構成を生成し、dry-runで検証してから強制する流れにも言及しています。IAMや実行権限の設定はMCP接続とは別に確認が必要です。

出典：[Google Cloud — Organization Policy MCP（11/12）](https://cloud.google.com/blog/products/identity-security/ai-powered-cloud-governance-whats-new-in-organization-policy)

## 9. 研究・ベンチマーク：MKAから評価の作り方を学ぶ

11月10日公開のMKAは、10分野・83職種に基づく200タスクで、視覚的に複雑な資料を扱うAgentを評価します。共通のStirrup HarnessでTools・Sandbox・Turn予算を揃え、成果物を専門家のRubricで評価します。

出典：[Google — MKA benchmark（11/10）](https://blog.google/innovation-and-ai/models-and-research/gemini-models/multimodal-knowledge-agent-benchmark/)

| 確認した設計 | 読み方 |
| --- | --- |
| 約70のYes/No基準を各タスクに用意 | 『良さそう』という総合印象を分解する |
| 事実の正確性75%、視覚設計25% | 正しい内容と、読みやすい見た目を別々に検査する |
| 専門家と自動評価の一致96%と公表 | モデルの正答率96%という意味ではない |
| 平均実行Turn数は比較対象間で約30〜130 | 品質だけでなく操作回数・時間・費用を比べる |

出典：[Google — MKA benchmark（11/10）](https://blog.google/innovation-and-ai/models-and-research/gemini-models/multimodal-knowledge-agent-benchmark/)

自分のレポート生成でも、出典URLが本文の主張を支えるか、更新日が一致するか、表が読めるか、ダウンロードできるかを個別に確認できます。本号のデザインを保ったまま内容を検証する、という目的にも近い考え方です。
