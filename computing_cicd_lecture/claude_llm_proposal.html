00 ― BACKGROUND

背景と全体像

モノリス・オンプレミス・ウォーターフォール開発からクラウドコンピューティング・アジャイル開発への変容が進む中、 変化の受容と加速するデリバリーへの対応には生産性向上と開発全体の柔軟性・機敏さが不可欠である。 この文脈でLLMが果たす役割は大きいが、従来の決定論的なシステム構成技術と異なり、 LLMは確率論的に出力を行うため、これまでとは異なる観点での評価・注意が求められる。

Client Situation

クラウド・アジャイルへ移行を始めたチーム。スクラム・クラウド技術の知識はあるが実績はない。

経営層より「AI実績」が新プロジェクトの目標として掲げられ、仕様駆動開発(SDD)の推進が決定している。

Core Tension

LLMの確率的出力特性を、決定論的な統制がなじむ大規模システム開発の中でどう安全に扱うか。

「AI実績」という経営要求が、利用量偏重のVanity Metricsに陥るリスク。

Discussion Outcome

A・B・Cそれぞれの提言が、独立した施策ではなく相互接続する一つの統制システムへ収束した。

三提言を貫く原則:
Authorityは付与するものではなく、Evidenceによって獲得し、異常時には自動的に失うもの。

02 ― PROPOSAL A

提言A

A

Delivery Architecture

仕様駆動開発を「Spec-to-Evidence 統制Pipeline」として構築する

仕様駆動開発をAIコード生成手法としてではなく、要求から実装・検証・証跡までを一貫して追跡できる Delivery Pipelineとして設計する。LLMには推論・生成を担わせ、決定論的な仕組みには判定・制約・実行を担わせる ―― Reasoning PlaneとControl Planeの分離を基本原則とする。

提言の目的

  • 要求から実装までのTraceability(追跡可能性)を確保する
  • AI生成物の検証可能性を確保し、確率的出力をそのままシステムリスクにしない
  • クラウド・アジャイル経験不足に起因する事故を構造的に抑制する
  • AI Agentが持つ権限(Authority)を、影響範囲に応じて統制する

具体的マイルストーン

Phase内容完了基準
M0Baseline測定(Lead Time / Change Failure Rate / MTTR等)最低1 Sprint分のBaselineを取得済み
M1AI利用境界の定義(Allow/Conditional/Deny)IAM・CI/CD・Repository Ruleとして機械的に強制できていること
M2SpecificationをSingle Source of Intentにする(Pilot機能)任意のコード変更をSpecificationまで逆引きできること
M3Deterministic Verification Gate構築(Test/SAST/SCA/Policy等)AI生成・人間生成を問わず同一Gateを通過しなければMerge不可
M4Spec-to-Evidence Pipeline完成、Agentic Developmentへ拡張Requirement→Spec→Code→Test→PR→CI→Deployment→Metricsを一つのTraceとして追跡可能

具体的なネクストアクション

  1. 本番影響の小さいFeatureを1件選定する
  2. Requirement → Specification → Acceptance Criteriaを作成する
  3. AI Agentには専用BranchとDev環境のみを付与する
  4. 作業時間・修正回数・レビュー時間・Defect・AI介入箇所を記録する
  5. 「品質を落とさずLead TimeをX%短縮できた」という実績を最初のゴールに据える
「AIを使いこなすこと」を最初の課題にしない。
最初に構築すべきは「AIが間違えても事故にならないSoftware Delivery System」である。

03 ― PROPOSAL B

提言B

B

Input & Observation Architecture

Executable Specとログ解析を組み込んだ「コンテキスト駆動型ガードレール」

仕様を対象の性質に応じたハイブリッド構造(Why=自然言語 / Business Rule=Gherkin / API=OpenAPI 等)で Executable化し、LLMには最小十分なコンテキストのみを渡す。加えてChat・Ticket等の非構造化ログを 継続的に解析し、仕様とコードのDriftを人間の意思決定前に検知する。

提言の目的とA案への補完ポイント

  • ウォーターフォール出身チームが巨大な自然言語仕様を投入し検証不能に陥るリスクを防ぐ
  • 仕様タイプごとに適した表現手段を使い分けるSpecification Type Systemを定義する
  • Chat/Jira等のコミュニケーションログをDrift検知に活用し、仕様の形骸化を防ぐ
  • ガードレールを「自動テスト」から「多角的なVerification Evidence」へ拡張する

具体的マイルストーン

Phase内容完了基準
Phase 1Specification Type Systemの定義とVerification Evidenceパイプライン構築仕様Type定義済み・CI Guardrail稼働・AI Authority境界定義済み・Baseline計測済み
Phase 2限定機能でのパイロット運用(仕様→テスト→コード生成サイクル)Traceability成立・Acceptance CriteriaへのEvidence存在・Lead Time/Defect Escape悪化なし
Phase 3スプリント標準プラクティスへの本格組み込み、Drift Detection拡大Evidence-based Promotionにより次段階のCapabilityへ順次拡張

具体的なネクストアクション

  1. 仕様記述を対象別(Why/Business Rule/API/Data/Architecture等)に定型化するワークショップを実施
  2. LLMへ渡すContextを「関連Requirement→Contract→ADR→Code→Test」のみに絞るMinimum Sufficient Context設計を導入
  3. Slack/Jira/PR/Commit/CI/Incident/WorklogのログをLLMで横断解析し、Drift Candidateを抽出する仕組みを構築
  4. Drift検知はPrecision/Recall双方で評価し、検出後は必ず人間の承認を経てSpecification更新に反映する

KPI(補正後)

指標内容
Verification Evidence網羅率Acceptance Criteriaに対して検証Evidenceが存在する割合(単純カバレッジ率から置換)
Critical Incident件数「バグ流出ゼロ」ではなくSeverity別(Critical=0件、Major/Minorは閾値運用)
Drift検知 Precision / Recall検知の的中率と見逃し率の双方を継続計測
Chat/Ticketは Signal であって Source of Truth ではない。
Drift Candidate は必ず人間の意思決定を経てSpecification変更に反映する。

04 ― PROPOSAL C

提言C

C

Delegation / Governance Architecture

Capability Registryによる段階的Authority委譲の構築

AI Agentへの権限付与を、システム単位・チーム単位の一括判断ではなく、Capability (AIへ委譲可能な操作・判断・生成・分析の最小統制単位)ごとにTrust Level(T0〜T3)を 独立して付与・運用する。昇格はEvidenceに基づく人間判断、降格はSeverity別の自動トリガーとする。

提言の目的

  • 権限を一括で拡大・収縮させる粗い運用による重大事故を構造的に排除する
  • AのDeterministic Gate、BのExecutable Spec/Drift Detectionを「どこまでAIに委ねてよいか」を継続管理するGovernance機構として接続する
  • 「AI実績」を利用量ではなく、安全に委譲できた業務領域の健全な成長と可逆性として説明可能にする
  • Drift Detectorのような監視機能自体もGovernance対象に含め、自己参照的に閉じた統制構造を実現する

Trust Level判定の考え方

Impact(影響範囲) × Detectability(検出可能性) × Recoverability(回復可能性)による Risk Classificationに加え、Production IAM変更・本番データ破壊操作・ Security Policy bypass等については成熟度に関わらず上限Trust Levelを固定する Explicit Deny Ruleを設ける。単純な積算スコアとしては扱わない。

Trust LevelAIの役割人間の関与
T1提案・生成のみ全変更を確認
T2Branch上で変更・Test実行Mergeを承認
T3低リスク変更を自律実行Exceptionのみ監督
T0 / Deny実行不可(Explicit Deny)常に人間が実行

具体的マイルストーン

Phase内容完了基準
M1Capability Registry設計(初期Trust Levelは原則T0/T1)パイロットScope内のCapabilityが100%登録。未登録Capabilityは Default Deny(Fail-Closed)
M2判定式に基づくGate成熟度連動Trust Level昇格条件が対応するVerification Evidence種別と明示的に紐付いていること
M3Promotion/Demotionフロー実装(昇格=Human Decision、降格=Severity別自動トリガー)Promotion実績1件以上、かつDemotion Drill(模擬降格演習)を実施済み
M4Drift Detection等の監視Capability自体の組み込み監視CapabilityのPrecision/Recallが定期計測され、閾値未達時に自動降格・Re-validationが機能すること

具体的なネクストアクション

  1. パイロット機能に関わるCapability(コード生成/Test生成/Branch操作/Spec変更提案等)を洗い出し、Registry初版を作成する
  2. 各Capabilityについて Impact・Detectability・Recoverability を暫定評価し、初期Trust Levelを設定する
  3. Critical/Major/Minorの降格トリガー一覧を確定し、CI/CD・監視基盤にアラートとして実装する
  4. Drift Detection機能をCapability Registryへ登録し、Precision/Recallの計測方法を確立する
  5. Capability Registryの状態(総数・Trust Level分布・昇格降格実績)を経営層向け報告に組み込む
Authorityは付与するものではなく、Evidenceによって獲得し、
異常時には自動的に失うものとする。 ―― No AI Capability is outside Governance.

05 ― KEY AGREEMENTS

ディスカウションにおける主要合意事項

A・B・C間で提起され、合意に至った主要な論点を時系列で整理する。

論点結論
Specificationのexecutable化の範囲 単一フォーマットに統一せず、Why=自然言語 / Business Rule=Gherkin / API=OpenAPI 等のハイブリッド構造(Specification Type System)とする 合意済
Human Reviewをどこまで削減できるか コードレビューは廃止せず、レビュー対象をRisk Basedに絞る。AI生成物であっても既存のSoftware Delivery Accountabilityに流す 合意済
Trust Levelを上げる条件 AIの性能ではなく、Impact × Detectability × Recoverability によるRisk Classification + Hard Constraint + Evidenceで判定。Capability単位で付与する 合意済
Communication LogのSpecification反映 Chat/Ticket → Drift Candidate → Human/Ruleによる Decision → Spec変更 → Test更新、という人間判断を挟むフローに限定する 合意済
Trust Levelの降格条件 昇格はHuman Decision、降格は原則Automatic。Critical即時／Major閾値超過／Minor監視強化のSeverity別設計とする 合意済
経営層の「AI実績」要求の置き換え AI利用率ではなく「AI適用可能Capability数」および「Capability Registryの健全な成長と可逆性(昇格・降格双方の実績)」で説明する 合意済
Drift Detector自体の継続監視 監視機能自体も独立したCapabilityとしてRegistryに登録し、Precision/Recallに基づき自動降格・Re-validationを適用する 合意済
Capabilityの定義 「業務機能の最小単位」ではなく「AIへ委譲可能な操作・判断・生成・分析の最小統制単位」へ修正 合意済
未登録Capabilityの扱い 全Capabilityの網羅登録を完了基準とせず、Registry未登録CapabilityはDefault Deny(Fail-Closed原則)とする 合意済

06 ― EXECUTIVE REPORTING

経営層向け報告フレーム

「AI実績」の要求を、利用量ではなく安全なデリバリー能力の拡張として説明するため、 以下の3層構造で定期報告を行う。

01 ― Business Outcome

デリバリー成果

  • Lead Time for Changes(Baseline対比の短縮率)
  • Change Failure Rate
  • Defect Escape Rate / Quality維持状況

02 ― AI Delegation

委譲状況

  • Capability総数
  • Trust Level分布(T0〜T3)
  • Promotion / Demotion実績件数

03 ― Governance Health

統制の健全性

  • Verification Evidence Coverage
  • Policy Violation件数
  • Drift Detection Coverage / Re-validation状況

07 ― CONCLUSION

結論

A(Delivery Architecture)・B(Input & Observation Architecture)・C(Delegation / Governance Architecture)の 三提言は、対立するものではなく、統合5層モデルとして完全に循環接続される一つのSoftware Delivery Control System として収束した。今回対象となるチームに対しては、この統合モデルを土台に、まず本番影響の小さいパイロット機能1〜2件で Intent→Spec→Generation→Verification→Governanceの全ループを実地検証することを推奨する。

Principle 01
Authorityは付与するものではなく、Evidenceによって獲得し、異常時には自動的に失うものとする。
Principle 02
No AI Capability is outside Governance. ―― Code Generatorであれ、Reviewerであれ、Drift Detectorであれ、統制の外に置かない。

AI導入の対象はDeveloper個人ではなく、Intent / Spec / Code / Test / CI/CD / IAM / Observability / Communication / Governance を含むSoftware Delivery Systemそのものである。この前提に立つ限り、Executable Spec(B)、Deterministic Gate(A)、 Capability-based Trust(C)は矛盾なく一つのアーキテクチャとして成立する。
