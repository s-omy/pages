対象組織 クラウド・スクラム未経験チーム

アーキテクチャ基本原則

「Reasoning Plane（AI）と Control Plane（決定論的システム）の分離」

LLMには曖昧な情報の構造化と分析（考えさせること）を担当させ、決定論的な検証基盤（CI/CD、テスト、ポリシー解析）に判定・制約・実行を行わせる。確率論的な成果物は直接本番環境へ接続せず、必ず決定論的なGateを通じて検証する。

1. 現状整理とリスク分析

観点 現状認識・課題 LLM活用の方向性・対策
開発スタイルの変容 ウォーターフォールの段階的変換から、アジャイルの短いフィードバックループへの変化。開発未成熟な状態で導入すると失敗を加速させる。 仕様・コード・テストの相互変換コストを下げ、ループを加速させる触媒として活用。変更バッチを最小化する。
現場での活用事例 コード補完、単体テスト生成、IaCテンプレート生成、PR一次レビュー等の個別適用が中心。 個別最適（Lines of Code）から、検証済み変更の提供速度（Validated Change / Lead Time）向上へシフト。
インシデントとリスク LLMへの不可逆権限付与によるデータ削除、ハルシネーション起因のSupply Chain Attack（Slopsquatting）。 生成コードは信用せず「検証結果」を信用する。AIへの権限付与は最小権限の原則（Least Privilege）を適用。
ミッションクリティカル適用 非決定性と応答遅延から、本番実行時ロジックへの直接組み込みは高リスク。 SDLC内（仕様定義、テスト作成、静的解析、障害解析）におけるHuman-in-the-Loop前提の適用。
コミュニケーションログ活用 Chat, Ticket, Commit等に散在する非構造化データが活用されず、仕様の形骸化（Spec Drift）が発生。 LLMがログを横断分析し「仕様と実装の不一致（Drift Candidate）」を検出。意思決定は人間が行う。

2. 統合モデル：「Software Delivery Control System」（5層構造）

A・B・C 3名の提言を統合し、開発プロセス全体を閉ループで統制する5層アーキテクチャとして定義する。

1. Intent Layer（意図・要求層） Human Led

人間が「何を、なぜ作るか」を定義する層。Business Intent、Requirement、Architecture Decision Record (ADR) を含む。

2. Specification Layer（仕様構造化・観測層） Member B 担当

Intentを検証可能な形へ変換する層。自然言語（Why）、Gherkin（Business Rule）、OpenAPI（API Contract）等のハイブリッド構造（Type System）で管理。最小十分なコンテキスト（Minimum Sufficient Context）のみを抽出して抽出・供給する。

3. Reasoning / Generation Layer（AI思考・生成層） Probabilistic Plane

LLMが設計候補、コード、テスト、レビュー案、Drift Candidateを生成する層。この出力を直接事実（Fact）として扱わず、候補として次層へ渡す。

4. Control / Evidence Layer（決定論的検証層） Member A 担当

Build, Unit/Integration Test, SAST, SCA, Secret Scan, Policy as Code等の自動実行により、100%決定論的に Verification Evidence を作成・判定する層。

5. Delegation / Governance Layer（権限委譲・統制層） Member C 担当

Capability単位でTrust Level（T0〜T3）を管理。昇格はEvidenceに基づく人間判断（Promotion）、降格はSeverity（Critical/Major/Minor）別の自動降格（Automatic Downgrade）で制御する。

3. 段階的実装マイルストーン

フェーズ マイルストーン概要 主な完了判定基準（Evidence）
Phase 0 Baseline（現状値）の測定 過去プロジェクトまたは最低1スプリントの Lead Time, Change Failure Rate, Rework率 の取得完了。
Phase 1 Capability Registry設計と境界定義 全AI関与機能がCapability登録され、初期Trust Level（T0/T1）と権限境界がCI/CD・IAMで強制されていること。
Phase 2 Specification Type System & Verification Gate構築 Gherkin/OpenAPI化の確立。LLM生成物に対する自動テスト・セキュリティスキャン等のEvidence生成率100%。
Phase 3 Traceability Pipeline & Drift Detection稼働 要求からDeployまで1本のTraceで追跡可能。Chat/Jiraログから仕様不整合（Drift Candidate）を検知可能。
Phase 4 Delegation Governance運用と自己監視の組み込み Drift Detector自身もCapabilityとして継続監視（Precision/Recall）。Severity別自動降格トリガーの検証完了。

4. 経営層向け「AI実績」要求の置換モデル

経営層が求める「AI利用率」「生成コード量」などの Vanity Metrics（虚栄の指標）を退け、デリバリー能力とガバナンス成熟度の持続的成長を示す**複合評価ビュー**へと翻訳・報告する。

報告軸 指標・提示内容 経営的価値
Capability Registry 推移 AI関与Capability総数、Trust Level（T0〜T3）分布状況 安全にAIへ委譲可能な業務領域の拡大範囲を視覚化
Delegation 可逆性実績 期間内の昇格件数、および自動降格（Demotion）の発生件数と要因 統制機構（Governance）が健全に機能していることの立証
Delivery Capability 改善 Lead Time for Changes（短縮率）、Change Failure Rate、Rework率 品質を維持・向上させた上での本質的な開発スピード向上
Traceability 達成度 Acceptance Criteria に対する Verification Evidence 網羅率 仕様と実装・テストの完全な透明性と説明責任の担保
