1. Executive Summary

本ディスカッションでは、LLMを単なるコード生成ツールとして導入するのではなく、Software Delivery System全体へ組み込むことが必要であるとの合意に至った。

LLMには考えさせ、決定論的な仕組みに判定・制約・実行させる。

そのため、要求・仕様・コード・テスト・CI/CD・IAM・Observability・コミュニケーションログ・Governanceを一体として扱い、LLMの確率的出力を決定論的な制御系の中へ封じ込める。

A：Delivery Architecture

Spec-to-Evidence Pipeline、Deterministic Verification、Reasoning Plane / Control Plane分離。

B：Specification / Context / Observation

Specification Type System、Minimum Sufficient Context、Communication Logを用いたDrift Detection。

C：Delegation Governance

Capability Registry、Trust Level、Evidence-based Promotion、Automatic Demotion、Default Deny。

2. 背景と現状認識

2.1 開発モデル変容におけるLLMの役割

従来のウォーターフォール型では、要求→要件→設計→実装→テスト→リリースを人間が段階的に変換してきた。一方、クラウド・アジャイル型では、要求→小さな仕様→実装→検証→デプロイ→観測→フィードバックという短いループが中心となる。

LLMの主価値はコード生成量ではなく、これら工程間の意味変換コストの削減にある。

2.2 主な活用領域

  • Requirement / User Story / Acceptance Criteriaの構造化
  • コード、テスト、IaC、文書の生成
  • PRレビュー、ログ解析、設計レビュー支援
  • チケット・チャット・作業ログからのリスク／Drift候補抽出
  • 障害初期解析、運用ログからの次アクション候補生成

2.3 LLM特有のリスク

  • ハルシネーションによる誤実装・不存在Dependency・脆弱Dependencyの混入
  • Prompt/Contextへの機密情報混入
  • ライセンス・Supply Chain・Security上の問題
  • Agentへ過大Authorityを付与することによる不可逆操作
  • 監視AI自身のFalse Positive / False Negative

3. 三者合意による統合原則

原則1： AI導入の対象はDeveloper個人ではなく、Software Delivery System全体である。
原則2： Reasoning Plane（AI）とControl Plane（決定論的システム）を分離する。
原則3： 生成物ではなくVerification Evidenceを信用する。
原則4： Specificationは巨大な単一文書ではなく、相互参照可能なSpecification Type Systemとして管理する。
原則5： LLMへ与えるContextはMaximum ContextではなくMinimum Sufficient Contextとする。
原則6： Chat / Ticket / LogはSignalでありSource of Truthではない。
原則7： AuthorityはEvidenceによって獲得し、異常時には原則自動的に失われる。
原則8： No AI Capability is outside Governance.
原則9： Registry未登録CapabilityはDefault Denyとする。

5. A提言：Spec-to-Evidenceの統制されたDelivery Pipeline

提言

仕様駆動開発をAIコード生成手法ではなく、「Spec-to-Evidenceの統制されたDelivery Pipeline」として構築する。

目的

  • RequirementからProductionまでのTraceability確保
  • AI生成物の検証可能性確保
  • Cloud / Agile未経験による事故抑制
  • AI AgentのAuthority制御
  • AI導入成果をDelivery Capabilityとして測定

中核設計

AIはReasoning / Generationを担当し、Merge・Deploy・Security・Policy判定などは決定論的Gateへ委譲する。AI生成コードも人間生成コードも同じ品質保証プロセスを通す。

7. C提言：Capability RegistryによるDelegation Governance

Capability定義

Capability = AIへ委譲可能な操作・判断・生成・分析の最小統制単位

Trust Levelの考え方

Level例Authority
T0未承認 / Explicit Deny実行不可
T1提案・生成Human確認必須
T2Branch変更、限定的Test実行等限定Authority
T3低リスク・高検証可能・高回復可能な領域条件付き自律実行

Authority判定

単純な数式ではなく、以下の4要素で判定する。

  • Risk Assessment：Impact / Detectability / Recoverability
  • Mandatory Controls
  • Verification Evidence
  • Explicit Deny Rules / Trust Level上限

Production IAM変更、本番データ破壊、Security Policy bypass、規制上Human Approval必須の操作等は、Gate成熟度に関係なく上限Authorityを固定する。

9. KPIと経営層向け「AI実績」の再定義

AI利用率、Prompt数、生成コード行数を主要KPIとしない。AIによってDelivery Systemがどう改善したかを示す。

Business Outcome Lead Time / Deployment Frequency / Change Failure Rate / Defect Escape / Rework
AI Delegation Capability総数 / Trust Level分布 / Promotion / Demotion / Human Override
Governance Health Evidence Coverage / Policy Violation / Detection Coverage / Re-validation / Drift Precision-Recall

重要な評価原則

  • Lead Time短縮はBaseline取得後の改善仮説として扱い、固定値30%を絶対KGIにしない。
  • Speed改善時もChange Failure Rate / Defect Escape Rateが悪化していないことを条件とする。
  • 「LLM起因バグゼロ」ではなく、Critical AI-related Incident 0、Major/MinorはSeverity別に追跡する。
  • Securityは「脆弱性検知率100%」ではなく、Mandatory Security Controls実行率100%、Critical Finding未解決0等で管理する。
  • 降格件数単体をPositive KPIにせず、Severity、Root Cause、再発防止、再昇格Lead Timeと組み合わせる。

10. 具体的なNext Actions

  1. 本番影響の低い1〜2機能をパイロット対象に選定する。
  2. 対象機能に関わるCapabilityを洗い出し、Registry初版を作る。
  3. Specification Type Systemと参照ルールを定義する。
  4. LLMへ渡すMinimum Sufficient Contextの選択ルールを実装する。
  5. CI/CDへUnit / Integration / Contract / SAST / SCA / Secret / IaC / Policy等のVerification Gateを組み込む。
  6. CapabilityごとのRisk / Mandatory Controls / Evidence / Explicit Denyを定義する。
  7. AI生成・人間生成に同一の品質保証プロセスを適用する。
  8. Communication LogからDrift Candidateを抽出する仕組みを限定導入する。
  9. Precision / RecallおよびFalse Negative監視を開始する。
  10. Promotion / Demotion Drillを実施し、Authority縮小→再検証→Human再昇格を確認する。
  11. 経営向け報告をBusiness Outcome / AI Delegation / Governance Healthの3層で作成する。

11. 結論

三者の提言は、最終的に一つの循環型アーキテクチャへ統合された。

Structured Intent → Controlled Generation → Deterministic Verification → Risk-based Delegation → Evidence → Observation → Feedback

このモデルでは、LLM導入は「AI Coding Toolを配布する施策」ではない。仕様、Context、コード、CI/CD、IAM、Observability、コミュニケーション、Governanceを一体化し、変更を小さく、速く、安全にProductionへ届ける能力そのものを高める取り組みとして位置づける。

最終的な成功条件は、AIの利用量ではなく、AIを含むSoftware Delivery Systemが、品質・速度・安全性・説明可能性を同時に向上させたかである。
